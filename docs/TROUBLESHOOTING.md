# Solución de problemas (todos ocurrieron en la sesión de referencia)

Antes de nada: `tools/status.sh` (muestra también pods `0/1 Running`, que `grep -v Running` oculta).

| # | Síntoma | Causa | Solución |
|---|---|---|---|
| 1 | `WARNING version.toml not found` y versión 26.0.0 | Los scripts de IBM buscan `version.toml` en el directorio **padre** del cwd | Ejecutar siempre desde `scripts/` (las fases ya lo hacen) |
| 2 | Model Gateway: error `IBMLicensingDefinition` | Falta el License Service (CRDs) | Fase 03 lo instala (`helm template --include-crds` → aplicar CRDs, esperar `Established`, aplicar el resto en `ibm-licensing` con el secreto `ibm-entitlement-key` copiado) |
| 3 | ccxadmin sin permisos de admin en el dominio P8 (`E_ACCESS_DENIED`); el operador reintenta "Create Content Process Engine P8 Domain" | El dominio se creó cuando el LDAP no devolvía `ibm-entryUuid` | Prevención: la fase 02 aplica `fix-ldap-guid.sh` **antes** de Content. Reparación: `tools/reset-gcd.sh` (borra `gcddb`, con respaldo; pide escribir `SI`) |
| 4 | `403 Forbidden` al aplicar métricas/CR de AI Services, MG o WDU desde el operador | La SA `ibm-content-operator-sa` no tiene permisos sobre esos CRDs | No usar `validate --apply`; la fase 05/06 aplica con `oc` (cluster-admin) |
| 5 | Ruta de Model Gateway → 503 / `model-gateway.py` no conecta | El router no confía en el certificado autofirmado del gateway (sin `destinationCACertificate` → 503) | **Corregido en la fase 06** (ver #25). Alternativa de administración: port-forward: `oc port-forward svc/model-gateway-service 8443:8080 -n <ns>`; `model-gateway.py config url https://localhost:8443` y `config insecure true` (la fase 06 lo hace) |
| 6 | Agente: `500 SYS_INTERNAL_ERROR`; en el log del Reasoning Service `403 SPACES0008E` | El Service ID de la API key no es colaborador del deployment space | Añadirlo (rol Editor). **No** hace falta cambiar nada en el gateway. Probar con `tools/test-wxai-key.py`. Para cambiar la clave de WDU: `tools/swap-wxai-key.py` |
| 7 | `PKIX path building failed` al correr `ccx_ai_metadata.sh` | Java no confía en la CA interna de CPE | Truststore PKCS12 con la cadena de la ruta de CPE + `JAVA_OPTS=-Djavax.net.ssl.trustStore=...` (lo hace `tools/ai-metadata.sh`) |
| 8 | `case.dir (and config.dir) not set` | `ccx_ai_metadata.sh` ejecutado fuera de `ccx-ai-services-metadata/` | Ejecutarlo desde esa carpeta (el script lo hace) |
| 9 | Rutas `/navigator/navigator/...` o validación `NAVIGATOR_EXTERNAL_URL must be the base URL` | URL con sufijo | `NAVIGATOR_EXTERNAL_URL=https://navigator-<ns>.<apps>` (sin `/navigator`). Si la ruta real difiere, la fase 08 avisa |
| 10 | El plug-in no encuentra el Reasoning Service | Server URL vacía/no guardada o con `/rsn` | Reguardar la URL en el plug-in, **sin** `/rsn` |
| 11 | Scripts con `set -euo pipefail` se detienen sin mensaje | `grep` sin coincidencias devuelve 1 | Usar `\|\| true` o quitar `pipefail` en esos pipes (ya aplicado en las herramientas) |
| 12 | `prerequisites.py validate` no resuelve DNS del cluster desde el bastión | El bastión no resuelve `*.svc.cluster.local` | Es opcional: si lo necesitas, ejecútalo dentro del pod del operador (copiar `scripts/`, `pip install -r requirements.txt` en `/tmp`, y **borrar** después los archivos copiados porque llevan contraseñas) |
| 13 | `ccx_ai_metadata.sh` devuelve 0 con una excepción Java | El script de IBM no propaga errores | `tools/ai-metadata.sh` revisa la salida y falla si hay excepciones |
| 14 | Login de Navigator falla con Keycloak / `invalid_client` | Cliente OIDC sin `serviceAccountsEnabled` o redirect URIs incorrectos | `tools/setup-keycloak.py "<redirect-uri>/*" ...` (idempotente, actualiza el cliente) |
| 15 | El IdP deja de ser de confianza (≈ 2027-01) | Caduca el certificado Let's Encrypt de la ruta de Keycloak | Borrar `ssl-certs/idp/*.pem`, volver a extraer la cadena (fase 05) y reaplicar `ssl/` |
| 16 | `CREATE ROLE ... already exists` al recargar la BD | `load-content-db.sh` no es idempotente | Se ejecuta una sola vez (marca `05-content-db`); para rehacer: `reset-gcd.sh` o recrear el cluster PG |
| 17 | `model-gateway.py patch-secret`: `FileNotFoundError: 'kubectl'` | OpenShift sin `kubectl` | La fase 01 crea un envoltorio `kubectl→oc` dentro del venv |
| 18 | ACCE en blanco | Caché/sesión del navegador | Ventana privada |
| 19 | El add-on de texto persistente no se aplica | A veces el primer *Install Add-on* no persiste | Repetir y verificar (clases `TxeTextExtractAnnotation` presentes) |
| 20 | `ImagePullBackOff` en operadores | Entitlement key inválida o sin derecho | `echo $KEY \| helm registry login cp.icr.io --username cp --password-stdin`; recrea el secreto `ibm-entitlement-key` |
| 21 | Fase 01: `helm: command not found` aunque se acaba de instalar | `/usr/local/bin` no está en el PATH de root (bastiones TechZone) | `lib/common.sh` lo añade al PATH; la fase 01 verifica Helm y enlaza `oc` en `/usr/local/bin` |
| 22 | `failed calling webhook "vpooler.pg.ibm.com" ... connection refused` | El selector de `ibm-pg-webhook-service` incluye también los pods de PostgreSQL (no escuchan en 9443): sólo 1 de N endpoints es el operador | `apply_retry` (lib/common.sh) reintenta ante ese error. A mano: repetir el `oc apply` en bucle. Posible defecto del chart de IBM de PG |
| 23 | Fase 07: "La salida contiene errores" aunque `CEMetadataCreator` terminó bien | El detector buscaba `E_[A-Z_]+` y coincidía con `SETTABLE_ONLY_ON_CREATE` | Corregido (palabra completa) y cada paso (`create`/`insert`) deja marca `07-meta-*` para no repetirse. Si ya corrió: `echo ok > .state/done/07-meta-create` |
| 24 | `legal-hold-mcp-server-route` responde 503 en la tabla de la fase 09 | Sin investigar (no afectó a Navigator, CPE ni al agente) | `oc get pods -n ibm-content \| grep -i legal` y `oc logs` del pod; probablemente irrelevante si no usas ese servidor MCP |
| 25 | `cas` (Content Assistant) falla con `503` al llamar a `https://model-gateway-<ns>.<apps>/v1/chat/completions` | La ruta `model-gateway` es *reencrypt* y el router no valida el cert del gateway (autofirmado, `CN=content ICP4A Root CA`, sin SAN); además el timeout por defecto es corto | La fase 06 hace `oc patch route model-gateway` con `spec.tls.destinationCACertificate` (cert del gateway) y la anotación `haproxy.router.openshift.io/timeout=300s`. Comprobar: `oc get route model-gateway -o jsonpath='{.spec.tls.destinationCACertificate}' \| head -c 40` |
| 26 | Embeddings por el gateway: `401 failed to fetch token` / `400 failed to get provider` | La API key de watsonx.ai guardada en el proveedor del gateway ya no existe (cuenta/TechZone nueva) o el modelo no está registrado | Probar la clave contra el space; borrar y recrear el proveedor con la clave nueva, registrar de nuevo los modelos y **repetir la clave en WDU**: `tools/swap-wxai-key.py` (cambia clave y space) |
| 27 | Pod `ibm-content-assistant-deployment` en CrashLoop: `CERTIFICATE_VERIFY_FAILED: CA cert does not include key usage extension` | El conector (Python 3.13) verifica en modo estricto: la CA debe tener `basicConstraints CA:TRUE` + `keyUsage keyCertSign`, el servidor SAN con el nombre del Service y SKI/AKI | `tools/gen-opensearch-certs.sh` ya genera todo (y verifica con `-x509_strict`). Si usas certificados propios, comprueba lo mismo. Las llaves deben ser PKCS#8 (`BEGIN PRIVATE KEY`) |
| 28 | `prerequisites.py validate` de Content Assistant: la base vectorial falla (sin SAN / no resuelve `.svc`) | Exige SAN con el host de la URL y el bastión no resuelve `*.svc` | La fase 08 no usa `validate`: valida OpenSearch con TLS desde dentro del pod y aplica los artefactos con `oc`. Ver también #12 |
| 29 | `ibmca login` → `FNRGA0001E Incorrect username or password, or insufficient privileges` | El login valida contra **OpenSearch** (no contra FileNet/LDAP): hace falta el usuario con el rol `ibm-genai-document-manager` | Usuario `genai-service-user` (lo crea la fase 08, paso 4). `ibmca login -u genai-service-user -p ...` (el `-u` es obligatorio) |
| 30 | Content Assistant responde "maxOutputTokens is too low" | `gpt-oss-120b` es de razonamiento: gasta los 4096 tokens de salida pensando | LLM de Content Assistant = `meta-llama/llama-3-3-70b-instruct` (`tools/cas-providers.py`). El Reasoning Service sigue con gpt-oss: con Llama 3.3 el agente de Navigator rechaza casi todo |
| 31 | Subo/edito documentos y no hay fragmentos en OpenSearch | (a) falta la suscripción `Document-Vector Index`; (b) cambiar sólo el título no dispara; (c) los documentos anteriores no se indexan | Crear la suscripción (MANUAL-STEPS §7). Disparan: documento **nuevo**, check-out/check-in. A veces llega en lote unos minutos después. Verificar: `tools/vector-index-check.sh`. El *custom sweep job* de IBM para documentos existentes: **no se pudo obtener/verificar** su procedimiento |
| 32 | Agente de Navigator: "network connectivity issue" intermitente | **Causa sin confirmar** (se vio un 500 y un 401 puntuales en el Reasoning Service; otras veces nada en logs) | Reintentar con *New chat* (el agente arrastra el primer documento como contexto). Revisar `oc logs deploy/ibm-reasoning-service-deploy` y el gateway en el momento del fallo |
| 33 | gpt-oss-120b se niega intermitentemente a devolver identificadores personales (CURP/RFC) | Comportamiento del modelo; resúmenes y preguntas de contenido sí responden | Reformular, o probar otro modelo en `ibm-providers-config-secret` (`llms[active_llm].model`) |
| 34 | Navegando en Navigator o ACCE (login por Keycloak), cada pocos minutos la página se recarga sola y vuelve a la página inicial; se pierde lo que se estaba haciendo | Liberty (Navigator/ACCE/GraphQL) usa `disable_ltpa_cookie=true` (defecto del operador) y `reAuthnOnAccessTokenExpire=true` (defecto de Liberty): la sesión web dura lo que el **access token** de Keycloak, que por defecto es de **5 min**. Al caducar, Liberty redirige a Keycloak, que contesta sin pedir contraseña (sesión SSO viva) y devuelve a la URL de inicio | **Corregido en `tools/setup-keycloak.py`** (fase 02): realm `ccx` con access token de 8 h, sesión SSO inactiva 8 h y máxima 12 h (`KC_ACCESS_TOKEN_LIFESPAN`, `KC_SSO_SESSION_IDLE`, `KC_SSO_SESSION_MAX`). En un ambiente ya instalado: `OC=oc NS=ibm-auth python3 tools/setup-keycloak.py` (sin argumentos no toca los redirect URIs), después **cerrar sesión y volver a entrar** (o ventana privada). No hace falta reiniciar pods. Comprobar: el script imprime la vida útil del token emitido (≈ 28800 s) |

## Diagnóstico útil
```bash
oc get fncmcluster content -n ibm-content -o json | jq '.status.conditions'
oc logs deploy/ibm-content-operator -n ibm-content --since=30m | grep -E "TASK|failed|FAIL" | tail -40
oc logs deploy/ibm-reasoning-service-deploy -n ibm-content --since=15m | grep -v "GET /health" | tail -60
oc get pods -n ibm-content | awk 'NR>1{split($2,a,"/"); if (a[1]!=a[2]) print}'
```
